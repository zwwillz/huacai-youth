# 后台页面性能与加载规范

本项目后台统一采用 **Structure first, data second（结构优先，数据随后）** 的页面开发原则。

这不是单页优化技巧，而是后续所有后台页面、新功能和重构都必须遵守的默认规范。

## 1. 用户点击后，先完成视觉导航

后台菜单、页面标题、当前模块和基础框架应立即切换，不得等待完整业务数据返回后才改变页面。

- Sidebar / Topbar 使用持久化 Layout。
- 目标菜单和标题应在导航开始时立即更新。
- 不允许让用户继续操作旧业务内容；导航期间旧区域必须禁用交互。
- **后台业务页面统一禁止用整页灰色 Skeleton 作为菜单切换的必经状态。**
- 目标 Server Component 尚未完成时，应立即显示目标页面自己的真实结构：标题、筛选、Tab、表头、卡片、表单字段和固定操作区先成立，只有数据位保持未完成状态。
- 登录页、打印页、抽签大屏等独立用途页面按自身用途处理，不套普通后台业务框架。

## 2. Loading 与完成态必须共享真实页面结构

这是后台加载体验的硬规则。

- **加载态和完成态应复用同一个 page-owned View / presentation component。**
- 两种状态应使用同一套核心 DOM 层级、className、尺寸规则和 CSS。
- Loading 只允许把未决数据替换为 `—`、`正在读取`、安全的空列表或固定占位值。
- 不允许在中央 Loading 文件里维护一套“看起来像最终页”的近似页面，然后在数据回来后整块换成另一套真实页面。
- Route Loading 的职责只是根据 URL **分发到目标页面自己的 View**，而不是重新发明目标页面的 UI。
- 固定 Hero、组别切换、阶段 Tab、发布状态条、操作栏、表头、卡片外框等，加载前后应保持原位。
- 页面真实 CSS 必须在持久 `/admin` Layout 中提前可用；不能等目标 Route 数据完成后才加载 CSS，导致第一帧尺寸或样式再次跳变。

如果某个成熟 Client 在加载模式下会产生缓存、请求或写操作副作用，应先抽出纯 View，或增加明确的 loading / preview 模式；不能为了复用 DOM 而污染真实业务状态。

## 3. 不依赖数据库的 UI 绝不能等待数据库

以下内容通常应直接渲染：

- 页面标题、说明、按钮和帮助文案。
- 表单字段、筛选框、Tab、表头和卡片外框。
- 固定操作入口和权限允许后即可确定的操作按钮。
- 已经存在于持久 Layout、当前浏览器会话或可靠本地缓存中的数据。

禁止为了获得一个默认数字、状态计数或列表数据，把整个页面包在一个顶层 `await getEverything()` 后面。

## 4. 页面按数据域渐进加载，而不是按组件乱拆请求

推荐结构：

1. **Static frame / real View**：真实页面结构立即显示。
2. **Light context**：当前赛事、组别、阶段、轻量统计等尽快补齐。
3. **Primary data**：当前列表、比赛、排名等主数据独立加载。
4. **Heavy / deep data**：详情、历史记录、大签表、PDF 等按需加载或预加载。

不要把每个小卡片拆成独立数据库请求。应按数据域聚合，让一次轻量 API / SQL 返回同一屏真正需要的一组数据。

对于已经有安全私有 API 的工作区，优先考虑：服务器只解析 session、访问范围和必要路由上下文，真实页面 Client 立即挂载，再由 API 把主业务数据填入同一个 View，而不是让顶层 Server Component 等完全部业务数据。

## 5. Stale-first / cache-first 只用于安全的会话内体验

后台数据不能进入公共 CDN 缓存。

允许：

- 浏览器当前会话内保存列表、详情和已读取的工作区数据。
- 返回旧页面时先显示会话缓存，再后台刷新。
- 清除搜索或关闭详情时直接恢复已存在的本地状态。

要求：

- 关键写操作后必须精确更新或失效对应缓存。
- 比分、晋级、排名等现场关键数据不能把过期缓存伪装成最新结果。
- 所有后台 API 默认 `private, no-store`，除非有明确、经过审查的其它策略。
- Loading 使用的安全空数据模型不得长期写入正式页面会话缓存，也不得触发业务写操作。

## 6. 默认值不是页面阻塞条件

创建类表单的默认值、建议编号、推荐日期等，如果可以由用户修改，就不应阻塞表单结构出现。

正确模式：

- 先用安全的本地默认值渲染完整表单。
- 后台获取“建议值”。
- 用户尚未编辑该字段时才自动补入建议值。
- 最终保存接口仍然重新做唯一性、权限和业务规则校验。

## 7. 现场业务页分层显示

比分、赛程、晋级、最终排名等页面优先保证：

- 当前赛事 / 组别 / 阶段上下文先成立。
- Hero、发布状态条、操作区域和筛选区域先出现。
- 轻量状态统计随后原位更新。
- 大列表、签表、完整比赛数据最后填充。

不能因为一张大表尚未返回，就把页面标题、组别选择和阶段控制一起隐藏，也不能先画一套完全不同的临时页面。

## 8. 登录、退出与认证页面也遵循 Structure first

登录页本身没有业务数据，不应等待数据库初始化状态后才显示。

- 登录页面结构、用户名/密码输入框、品牌与说明直接渲染。
- 首次管理员 setup 状态可以在页面出现后后台确认。
- `/admin/login` 不使用白色全屏 Route Loading。
- 登录按钮在提交后必须保持明确状态；认证成功后一直显示“正在进入工作台”，直到路由真正完成。
- 登录成功跨越“未登录页面 → 私有后台 Layout”边界时，使用文档级进入 `/admin`，确保新 session 在服务端重新建立完整持久 Shell。
- 点击退出登录后，欢迎登录结构必须立即出现；远端 Session 撤销和 Cookie 清理可以继续在后台请求中完成，在真正完成前登录表单保持禁用。
- 可以合并安全等价的认证数据库往返，但不得降低 bcrypt 强度、登录限流、session 随机性或账号状态校验。

## 9. 路由与数据请求是两件事

目标体验：

`点击 → 最终页面结构已经成立 → 轻数据原位补齐 → 主数据原位补齐 → 深层数据按需`

而不是：

`点击 → 近似页面 / 灰色骨架 → 等全部 SQL / API → 换成另一套最终页面`

## 10. 不允许用“全量预取”换取假快

Structure first 不等于提前请求所有后台数据。

- 工作台、创建赛事等轻页面可以主动预取。
- 比分、签表、晋级、最终排名等重页面默认只在明确用户意图后请求。
- 不为了缩短一次点击等待，重新制造大量 EdgeOne → Supabase 并发请求。
- 优先改善页面成立时间，再针对真实慢数据域优化 API / SQL / 缓存。

## 11. 性能优化不能绕过权限和一致性

- 持久 Layout 不能替代服务端权限校验。
- 写接口仍必须使用服务端 session viewer 和业务权限检查。
- Loading 模型只允许固定文案和安全占位值，不能嵌入未授权赛事、球员、账号或比赛数据。
- 不为了减少几次数据库往返，把高风险事务拆坏或取消并发保护。
- UI 可以先显示，敏感数据必须等通过权限验证后再返回。

## 12. 新后台页面开发检查清单

提交新页面或重构前逐项检查：

- [ ] 页面真实 View 是否能在主业务数据之前显示？
- [ ] Loading 与完成态是否复用同一个 page-owned View / 核心 DOM / CSS？
- [ ] Route Loading 是否只负责路由分发，而没有另外画一套近似页面？
- [ ] 固定 Hero、筛选、Tab、表头、发布条、按钮区是否加载前后保持原位？
- [ ] 真实页面 CSS 是否在切换第一帧已经可用？
- [ ] 是否存在不必要的顶层 `await` 阻塞整个页面？
- [ ] 是否把已有 Layout / 会话数据又查了一次？
- [ ] 是否可以把多个小查询合成一个轻量数据域查询？
- [ ] 搜索、筛选、分页、详情关闭是否只更新局部区域？
- [ ] 是否为返回页面保留了安全的会话缓存？
- [ ] Loading 空数据是否可能污染正式缓存或触发副作用？
- [ ] PDF、大签表、历史详情等是否保持按需加载？
- [ ] 是否避免无必要地预取重页面？
- [ ] 后台 API 是否仍是私有、不可公共缓存？
- [ ] 写操作后是否正确更新 / 失效本地数据？
- [ ] 登录 / 退出 / 保存按钮在异步阶段是否保持稳定状态？
- [ ] TypeScript、ESLint、Production Build 是否全部通过？

## 13. 当前统一样板

- `/admin` 工作台：**真实 Dashboard 结构 + async summary widgets**。
- `/admin/events/new` 创建赛事：**真实表单 + async suggested defaults**。
- `/admin/login` 登录：**Immediate login frame + async setup state + stable submit transition**。
- `/admin/competition` 竞赛总览：**同一个 CompetitionOverviewView 贯穿加载态与完成态；主业务数据由私有 API 原位填入**。
- `/admin/competition/schedules` 赛程索引：**同一个 ScheduleIndexView 贯穿加载态与完成态**。
- `/admin/competition/scoring` 比分录入：**同一个 ScoringWorkspaceView 贯穿加载态与完成态，比分卡片只替换真实数据位**。
- 抽签、晋级、最终排名：**Loading 直接复用正式 Draw / Qualification / MainRoster / FinalRanking 组件的安全空数据模式**。
- 赛事管理 / 赛事设置 / 内容发布 / 参赛提示 / 球员档案 / 积分排名 / 账号权限 / 操作日志：**Loading 复用各自正式 View 或 Client，不再由中央 Loading 画近似界面**。
- `/admin` 持久 Layout：**即时导航 + 真实页面 CSS 常驻 + Route Loading 只分发页面自己的 View**。

以后新增或优化任何后台页面，都必须先判断“哪些结构与数据无关”，并优先让这些结构立即成立；如果已经有最终页面组件，优先让 Loading 直接复用它，而不是再做第二套占位页面。
