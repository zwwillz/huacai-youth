# 后台页面性能与加载规范

本项目后台统一采用 **Structure first, data second（结构优先，数据随后）** 的页面开发原则。

这不是单页优化技巧，而是后续所有后台页面、新功能和重构都必须遵守的默认规范。

## 1. 用户点击后，先完成视觉导航

后台菜单、页面标题、当前模块和基础框架应立即切换，不得等待完整业务数据返回后才改变页面。

- Sidebar / Topbar 使用持久化 Layout。
- 目标菜单和标题应在导航开始时立即更新。
- 不允许让用户继续操作旧业务内容；导航期间旧区域必须禁用交互。
- 完整页面 Skeleton 仅作为冷启动、异常慢请求或尚未完成局部化改造页面的兜底。
- **不要为了证明“系统正在加载”而主动闪 Skeleton。** 快路由应直接落到真实页面。
- 当前默认阈值：普通后台路由约 **180ms** 后才显示路由级 Skeleton；工作台、创建新赛事等 structure-first 页面约 **360ms** 后才启用兜底 Skeleton。阈值以后可以按真实 Chrome 数据调整，但原则不变：短请求不显示全页骨架。

## 2. 不依赖数据库的 UI 绝不能等待数据库

以下内容通常应直接渲染：

- 页面标题、说明、按钮和帮助文案。
- 表单字段、筛选框、Tab、表头和卡片外框。
- 固定操作入口和权限允许后即可确定的操作按钮。
- 已经存在于持久 Layout、当前浏览器会话或可靠本地缓存中的数据。

禁止为了获得一个默认数字、状态计数或列表数据，把整个页面包在一个顶层 `await getEverything()` 后面。

## 3. 页面按数据域渐进加载，而不是按组件乱拆请求

推荐结构：

1. **Static frame**：页面结构立即显示。
2. **Light context**：当前赛事、组别、阶段、轻量统计等尽快补齐。
3. **Primary data**：当前列表、比赛、排名等主数据独立加载。
4. **Heavy / deep data**：详情、历史记录、大签表、PDF 等按需加载或预加载。

不要把每个小卡片拆成独立数据库请求。应按数据域聚合，让一次轻量 API / SQL 返回同一屏真正需要的一组数据。

## 4. Stale-first / cache-first 只用于安全的会话内体验

后台数据不能进入公共 CDN 缓存。

允许：

- 浏览器当前会话内保存列表、详情和已读取的工作区数据。
- 返回旧页面时先显示会话缓存，再后台刷新。
- 清除搜索或关闭详情时直接恢复已存在的本地状态。

要求：

- 关键写操作后必须精确更新或失效对应缓存。
- 比分、晋级、排名等现场关键数据不能把过期缓存伪装成最新结果。
- 所有后台 API 默认 `private, no-store`，除非有明确、经过审查的其它策略。

## 5. 默认值不是页面阻塞条件

创建类表单的默认值、建议编号、推荐日期等，如果可以由用户修改，就不应阻塞表单结构出现。

正确模式：

- 先用安全的本地默认值渲染完整表单。
- 后台获取“建议值”。
- 用户尚未编辑该字段时才自动补入建议值。
- 最终保存接口仍然重新做唯一性、权限和业务规则校验。

## 6. 现场业务页分层显示

比分、赛程、晋级、最终排名等页面优先保证：

- 当前赛事 / 组别 / 阶段上下文先成立。
- 操作区域和筛选区域先出现。
- 轻量状态统计随后出现。
- 大列表、签表、完整比赛数据最后填充。

不能因为一张大表尚未返回，就把页面标题、组别选择和阶段控制一起隐藏。

## 7. 登录与认证页面也遵循 Structure first

登录页本身没有业务数据，不应等待数据库初始化状态后才显示。

- 登录页面结构、用户名/密码输入框、品牌与说明直接渲染。
- 首次管理员 setup 状态可以在页面出现后后台确认。
- `/admin/login` 不使用白色全屏 Route Loading。
- 登录按钮在提交后必须保持明确状态；认证成功后一直显示“正在进入工作台”，直到路由真正完成，不能中途恢复成可点击状态造成“是不是登录失败”的错觉。
- 登录成功后进入后台，持久 Shell 只阻塞在真正必要的 session 身份验证上；赛事导航等非必要上下文随后由页面或局部数据补齐。
- 可以合并安全等价的认证数据库往返，但不得降低 bcrypt 强度、登录限流、session 随机性或账号状态校验。

## 8. 路由与数据请求是两件事

目标体验：

`点击 → 页面成立 → 轻数据补齐 → 主数据补齐 → 深层数据按需`

而不是：

`点击 → 等全部 SQL / API → 整页突然出现`

## 9. 性能优化不能绕过权限和一致性

- 持久 Layout 不能替代服务端权限校验。
- 写接口仍必须使用服务端 session viewer 和业务权限检查。
- 不为了减少几次数据库往返，把高风险事务拆坏或取消并发保护。
- UI 可以先显示，敏感数据必须等通过权限验证后再返回。

## 10. 新后台页面开发检查清单

提交新页面或重构前逐项检查：

- [ ] 页面框架是否能在主业务数据之前显示？
- [ ] 是否存在不必要的顶层 `await` 阻塞整个页面？
- [ ] 快页面是否因为 Route Loading 产生了不必要的 Skeleton 闪烁？
- [ ] 是否把已有 Layout / 会话数据又查了一次？
- [ ] 是否可以把多个小查询合成一个轻量数据域查询？
- [ ] 搜索、筛选、分页、详情关闭是否只更新局部区域？
- [ ] 是否为返回页面保留了安全的会话缓存？
- [ ] PDF、大签表、历史详情等是否保持按需加载？
- [ ] 后台 API 是否仍是私有、不可公共缓存？
- [ ] 写操作后是否正确更新 / 失效本地数据？
- [ ] 登录/保存按钮在成功跳转前是否保持稳定的 pending 状态？
- [ ] TypeScript、ESLint、Production Build 是否全部通过？

## 11. 当前样板

- `/admin` 工作台：**Static frame + async summary widgets**。
- `/admin/events/new` 创建赛事：**Static-first form + async suggested defaults**。
- `/admin/login` 登录：**Immediate login frame + async setup state + stable submit transition**。
- `/admin/players` 球员管理：**局部列表请求 + 会话缓存 + 即时详情框架**。
- `/admin` 持久 Layout：**即时导航 + 延迟路由 Skeleton 兜底**。

后续赛事管理、内容发布、竞赛执行、比分、晋级、最终排名等页面应逐步按照本规范迁移，而不是重新发明另一套加载模式。
